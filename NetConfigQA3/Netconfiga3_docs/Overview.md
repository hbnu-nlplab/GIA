# NetConfigQA3: 시스템 설계 Overview

> **목적**: 랩미팅 발표용 총정리 문서  
> **날짜**: 2026-01-07  
> **대상**: SIGCOMM 제출 목표

---

## 1. 프로젝트 개요

### 1.1 문제 정의

**NetConfigQA2의 한계**: 장비 100대 규모에서 **컨텍스트 폭발** 발생

| 문제              | 원인                         | 영향                      |
| ----------------- | ---------------------------- | ------------------------- |
| Context 과부하    | 모든 Facts를 프롬프트에 주입 | 토큰 한계 초과, 비용 증가 |
| 정보 손실         | LLM이 전체 정보 기억 불가    | 정확도 저하               |
| 비효율적 업데이트 | Config 변경 시 전체 재로드   | 불필요한 반복 작업        |
| 도구 선택 혼란    | 32개 API 직접 노출           | 잘못된 도구 선택          |

### 1.2 해결 방향: NetConfigQA3

**핵심 전환**: Facts를 "프롬프트"에서 "**질의 가능한 메모리**"로 변경

```
[NetConfigQA2]                    [NetConfigQA3]
전체 Facts → LLM    ──────→    LLM ← 질의 → Facts DB
(Context 폭발)                  (필요한 것만 가져옴)
```

### 2.2 레이어별 역할

| 레이어                | 구성요소                           | 역할                                  |
| --------------------- | ---------------------------------- | ------------------------------------- |
| **Agent Layer**       | Reasoner, Retriever                | 추론/판단, 증거 수집 분리             |
| **HITL Layer**        | Approval Gate, Checkpoints, Alerts | 안전 장치, 중간 개입, 실시간 모니터링 |
| **Query Tools Layer** | facts/batfish/nso/logs.query       | 통합 질의 인터페이스 (5~8개로 제한)   |
| **Data Layer**        | Static Facts DB, Dynamic Telemetry | 정적/동적 데이터 분리 저장            |

## 3. 핵심 원칙 (3가지)

### 3.1 원칙 1: 계층적 정보 제공 (지도 기반 탐색)

```
┌────────────────────────────────────────────────┐
│           Level 1: 네트워크 지도               │
│           (수십 줄, 상시 보유)                 │
│  - 장비 수/역할 (PE/P/Leaf/Spine)             │
│  - VRF 목록, AS 번호                          │
│  - 중요 서비스 목록                            │
│  - 사용 가능한 도구 카탈로그                   │
└──────────────────────┬─────────────────────────┘
                       │ 질문 시 요청
                       ▼
┌────────────────────────────────────────────────┐
│         Level 2: Evidence Pack                 │
│         (수백~천 토큰, 선택적 가져옴)          │
│  - 질문에 직접 관련된 정보만 포함              │
│  - 예: "pe1의 VRF_AI RT?" → pe1의 VRF_AI만    │
└────────────────────────────────────────────────┘
```

**효과**: 평소엔 "지도"만 들고, 질문 시 필요한 정보만 가져옴 → **컨텍스트 절약**

### 3.2 원칙 2: 데이터 저장소 분리

```
┌─────────────────────────┐    ┌─────────────────────────┐
│    Static Facts DB      │    │  Dynamic Telemetry      │
├─────────────────────────┤    ├─────────────────────────┤
│ • CFG에서 추출한 구조적  │    │ • 시간축 데이터         │
│   사실                   │    │   (로그/메트릭/플로우)  │
│ • VRF, BGP neighbor,    │    │ • 계속 변하는 활성      │
│   ACL, 인터페이스 주소   │    │   데이터                │
│ • 스냅샷 기반            │    │ • 시간 조건 필수        │
└───────────┬─────────────┘    └───────────┬─────────────┘
            │                              │
            └──────────┬───────────────────┘
                       ▼
            ┌──────────────────────┐
            │    Evidence Pack     │
            │   (통일된 출력 포맷)  │
            └──────────────────────┘
```

**핵심**: 저장소는 분리, **컨텍스트 출력 포맷은 통일**

### 3.3 원칙 3: 도구 표면적 최소화 (메가툴 패턴)

```
┌─────────────────────────────────────────────────────────┐
│              LLM이 보는 도구 (5~8개)                    │
├─────────────────────────────────────────────────────────┤
│  facts.query(query, filters, fields, limit)            │
│  batfish.query(name, params)                            │
│  batfish.diff(name, params, base, candidate)           │
│  nso.get(device, path, source)                          │
│  nso.txn(action, payload)  ⚠️ 승인 필요                │
│  logs.query / metrics.query / flows.query              │
└─────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│        내부 구현 (수십 개 함수)                         │
│  - enter_nso.py (32개 API)                             │
│  - Batfish template registry (다양한 분석)              │
│  - Telemetry collectors                                 │
└─────────────────────────────────────────────────────────┘
```

**핵심**: 내부는 복잡해도, **LLM에게는 소수 도구만 노출**

## 7. Skills 모듈화

### 7.0 Skills란? (일반 에이전트와의 차이)

**Skills** = 에이전트가 특정 상황에서 참조하는 **도메인 지식 + 행동 규칙 모음**

```
┌────────────────────────────────────────────────────────────────────────┐
│           일반 에이전트 vs Skills 기반 에이전트 비교                   │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│   [일반 에이전트]                    [Skills 기반 에이전트]            │
│                                                                        │
│   ┌─────────────────────────┐       ┌─────────────────────────┐       │
│   │  System Prompt          │       │  System Prompt          │       │
│   │  (거대한 하나의 문서)    │       │  (최소한)               │       │
│   │                         │       │                         │       │
│   │  • 모든 도구 설명       │       │  • 기본 역할만 기술      │       │
│   │  • 모든 규칙            │       │                         │       │
│   │  • 모든 시나리오        │       │                         │       │
│   │  • 모든 예시            │       └─────────────────────────┘       │
│   │                         │                   │                      │
│   └─────────────────────────┘                   ▼                      │
│              │                       ┌─────────────────────────┐       │
│              ▼                       │   Skills (분리된 모듈)   │       │
│   ┌─────────────────────────┐       │                         │       │
│   │ LLM에게 전체 주입       │       │  상황에 맞는 것만 로드   │       │
│   │                         │       │  ┌───────┐ ┌───────┐   │       │
│   │ • 토큰 낭비             │       │  │ Core  │ │Batfish│   │       │
│   │ • 정보 과부하           │       │  │Policy │ │ Skill │   │       │
│   │ • 무관한 규칙도 보임    │       │  └───────┘ └───────┘   │       │
│   │ • 수정 시 전체 변경     │       │                         │       │
│   └─────────────────────────┘       └─────────────────────────┘       │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

**핵심 차이점**

| 항목              | 일반 에이전트                  | Skills 기반 에이전트        |
| ----------------- | ------------------------------ | --------------------------- |
| **프롬프트 구조** | 하나의 거대한 시스템 프롬프트  | 핵심 + 분리된 스킬 모듈     |
| **컨텍스트 효율** | 항상 전체 규칙 로드            | 필요한 스킬만 선택적 로드   |
| **유지보수**      | 수정 시 전체 영향              | 개별 스킬만 수정            |
| **재사용성**      | 낮음                           | 높음 (스킬 조합 가능)       |
| **일관성**        | 긴 프롬프트에서 규칙 간과 가능 | 명시적 규칙으로 일관성 유지 |
| **도메인 전문성** | 일반적 지식                    | 도메인 특화 규칙            |

### 7.2 Skill 예시 1: Core Policy Skill (상시 적용)

**용도**: 모든 에이전트가 항상 참조하는 기본 규칙

```markdown
# Core Policy Skill

## 역할

NetConfigQA3 에이전트의 핵심 행동 규칙을 정의합니다.
이 스킬은 **항상 적용**되며, 다른 모든 스킬보다 우선합니다.

---

## 1. Evidence Pack 규칙

### 상한 제한

- **Log Events**: 최대 30개
- **Metric Windows**: 최대 20개
- **Facts Records**: 최대 40개
- **Batfish Results**: 결과 행 최대 50개

### 금지 행동

- ❌ 전체 테이블 덤프 요청 (`SELECT * FROM device` 금지)
- ❌ 필터 없는 대량 질의
- ❌ 같은 질의 반복 (캐시 사용)

---

## 2. 캐시 우선 정책

### 규칙

1. 동일한 (snapshot_id, query, params) 조합은 **재질의 금지**
2. 캐시 히트 시 이전 결과 재사용
3. 캐시 미스 시에만 실제 질의 수행

### 예시
```

// 첫 번째 요청: 실제 질의
batfish.query("reachability", {src: "10.1.1.1", dst: "10.2.2.2"})
→ 결과 반환 + 캐시 저장

// 두 번째 요청: 캐시 사용
batfish.query("reachability", {src: "10.1.1.1", dst: "10.2.2.2"})
→ 캐시에서 반환 (질의 없음)

```

---

## 3. 추가 질의 제한

### 규칙
- 한 턴에 **추가 질의는 최대 1회**만 허용
- 정보가 부족하면 현재 Evidence Pack으로 최선의 답변 시도
- 무한 탐색 방지

### 허용 예시
```

[1] 초기 질의: facts.query("vrf", {device: "pe1"})
[2] 추가 질의 (1회): batfish.query("reachability", {...})
[3] 더 이상 질의 불가 → 결론 도출

```

---

## 4. 승인 필요 작업

### High-Risk (승인 필수)
- `nso.txn(action="commit", ...)`
- `nso.txn(action="rollback", ...)`
- `nso.txn(action="sync-to", ...)`
- 5대 이상 장비 동시 변경

### Critical (절대 불허)
- `any-any permit` ACL
- 무단 default route 추가
- 전체 BGP clear/reset

### Low-Risk (자동 허용)
- 모든 읽기 질의 (facts, batfish, logs, metrics)
- `nso.get()` (상태 조회)
```

### 7.3 Skill 예시 2: Batfish Tool Playbook (도구별)

**용도**: Batfish 도구를 언제, 어떻게 사용하는지 안내

````markdown
# Batfish Tool Playbook

## 역할

네트워크 분석 도구 Batfish의 올바른 사용법을 안내합니다.

---

## 1. 사용 가능한 템플릿

| 템플릿 이름                | 용도                | 필수 파라미터             |
| -------------------------- | ------------------- | ------------------------- |
| `reachability`             | 경로 도달 가능 여부 | src, dst                  |
| `traceroute`               | 경로 추적           | src, dst                  |
| `bgpPeers`                 | BGP 피어 상태 조회  | node (선택)               |
| `routeTable`               | 라우팅 테이블 조회  | node, vrf (선택)          |
| `differentialReachability` | 변경 전후 비교      | src, dst, base, candidate |

---

## 2. 언제 어떤 템플릿을 쓰나?

### 상황별 선택 가이드

| 사용자 질문                       | 사용할 템플릿              |
| --------------------------------- | -------------------------- |
| "A에서 B로 통신 되나요?"          | `reachability`             |
| "A에서 B까지 어떤 경로로 가나요?" | `traceroute`               |
| "BGP 세션 상태가 어떤가요?"       | `bgpPeers`                 |
| "pe1의 라우팅 테이블 보여줘"      | `routeTable`               |
| "이 변경이 통신에 영향 주나요?"   | `differentialReachability` |

---

## 3. 파라미터 규칙

### src/dst 형식

```json
// IP 주소 사용
{"src": "10.1.1.1", "dst": "10.2.2.2"}

// 장비명 + 인터페이스 사용
{"src": "pe1[GigabitEthernet0/0]", "dst": "ce1[GigabitEthernet0/0]"}

// 서브넷 사용
{"src": "10.1.0.0/24", "dst": "10.2.0.0/24"}
```
````

### 필터 사용

```json
// 특정 프로토콜만
{"protocol": "tcp", "dstPort": 443}

// 특정 VRF만
{"vrf": "VRF_AI"}
```

---

## 4. 결과 해석

### 성공

```
ACCEPTED
```

→ 패킷이 목적지에 도달함

### 실패

```
DENIED_IN (acl: deny-list, line: 100)
```

→ ACL에 의해 차단됨

```
NO_ROUTE
```

→ 라우팅 테이블에 경로 없음

```
LOOP
```

→ 라우팅 루프 발생

---

## 5. diff 사용 시 주의사항

### base vs candidate

- `base`: 현재 운영 중인 설정 (변경 전)
- `candidate`: 적용할 예정인 설정 (변경 후)

### 예시

```json
batfish.diff("differentialReachability", {
  "src": "10.1.1.1",
  "dst": "10.2.2.2",
  "base": "snapshot_current",
  "candidate": "snapshot_proposed"
})
```

### 결과

| Flow | Base 결과 | Candidate 결과 | 영향         |
| ---- | --------- | -------------- | ------------ |
| A→B  | ACCEPTED  | DENIED         | ⚠️ 통신 끊김 |
| C→D  | DENIED    | ACCEPTED       | ✅ 통신 복구 |

````

### 7.4 Skill 예시 3: BGP Issue Analysis Runbook (시나리오별)

**용도**: BGP 문제 발생 시 단계별 분석 절차

```markdown
# BGP Issue Analysis Runbook

## 역할
BGP 관련 문제 진단 시 따라야 할 **단계별 절차**를 안내합니다.

---

## 트리거 조건
- 사용자가 "BGP 세션이 안 올라와요" 같은 질문
- 알림: `BGP_SESSION_DOWN` 이벤트 발생
- Batfish 결과에서 `NO_ROUTE` 또는 `UNREACHABLE`

---

## 1단계: 현재 상태 파악

### 1.1 BGP 피어 상태 조회
```json
batfish.query("bgpPeers", {"node": "<문제 장비>"})
````

### 1.2 확인 사항

- [ ] 피어 IP가 올바른가?
- [ ] Remote AS가 맞는가?
- [ ] 세션 상태가 Established인가?

---

## 2단계: 관련 이벤트 수집

### 2.1 최근 로그 조회

```json
logs.query({
  "device": "<문제 장비>",
  "signature": "BGP*",
  "time_range": "1h"
})
```

### 2.2 흔한 이벤트 패턴

| signature                   | 의미             |
| --------------------------- | ---------------- |
| `BGP_SESSION_DOWN`          | 세션 끊김        |
| `BGP_NOTIFICATION_RECEIVED` | 피어가 알림 보냄 |
| `BGP_HOLD_TIMER_EXPIRED`    | 응답 없음        |
| `BGP_NEIGHBOR_STATE_CHANGE` | 상태 변경        |

---

## 3단계: 설정 검증

### 3.1 Facts DB에서 설정 확인

```json
facts.query("bgp_neighbor", {
  "device": "<문제 장비>",
  "neighbor_ip": "<피어 IP>"
})
```

### 3.2 체크리스트

- [ ] `remote_as` 값이 상대방과 일치하는가?
- [ ] `update_source` 인터페이스가 올바른가?
- [ ] `password` 설정이 양쪽에 동일한가?
- [ ] VRF가 올바른가? (VRF 간 피어링인 경우)

---

## 4단계: 연결성 테스트

### 4.1 Reachability 확인

```json
batfish.query("reachability", {
  "src": "<로컬 BGP IP>",
  "dst": "<피어 BGP IP>"
})
```

### 4.2 예상 결과

- `ACCEPTED` → 연결 OK, 설정 문제 가능성
- `DENIED_*` → ACL 차단, 해당 ACL 수정 필요
- `NO_ROUTE` → 라우팅 문제, IGP 확인 필요

---

## 5단계: 해결책 제안

### 5.1 흔한 원인과 해결책

| 원인                 | 증상                        | 해결책                            |
| -------------------- | --------------------------- | --------------------------------- |
| Remote AS 불일치     | `NOTIFICATION: Bad Peer AS` | 설정 수정                         |
| TCP 179 차단         | `CONNECT` 상태 유지         | ACL에 `permit tcp any any eq 179` |
| MD5 비밀번호 불일치  | 세션 즉시 끊김              | 양쪽 비밀번호 확인                |
| Update-source 미설정 | 세션 불안정                 | Loopback으로 설정                 |
| eBGP multihop 누락   | 직접 연결 아닌 경우 실패    | `ebgp-multihop` 추가              |

---

## 6단계: 변경안 생성 (필요 시)

### 6.1 변경 전 검증 필수

```json
// dry-run으로 먼저 확인
nso.txn(action="dry-run", ...)
```

### 6.2 Batfish diff로 영향 분석

```json
batfish.diff("differentialReachability", {
  "base": "current",
  "candidate": "proposed"
})
```

```
    ↓
```

```

### 10.6 Ablation Study 대상

| 구성요소           | 비교                    | 측정                     |
| ------------------ | ----------------------- | ------------------------ |
| Retriever          | 없음 vs 있음            | Context 효율, 정확도     |
| Cache              | 없음 vs 있음            | 툴 호출 수, 지연         |
| Mega-tool          | 개별 노출 vs 통합       | 도구 선택 오류율         |
| 승인 게이트        | on vs off               | 위험 행동률, Safety 점수 |
| Evidence Pack 상한 | 제한 없음 / 중간 / 엄격 | 토큰 대비 정확도         |
```
