\section{NetConfigQA 2.1}

Evaluating the ability of LLMs in network domains requires a benchmark that goes beyond simple knowledge-based QA and measures multi-step cognitive abilities, such as fact extraction from real configuration files, path inference, and fault impact analysis.
To this end, we construct \textbf{NetConfigQA~2.1}, a benchmark that automatically generates QA pairs across five cognitive difficulty levels from real-world Cisco IOS configuration files (\texttt{.cfg}).
NetConfigQA~2.1 consists of four components: topology design, a Dual-Path generation pipeline, a cognitive difficulty taxonomy, and TA-Acc, an evaluation metric specialized for network data.

% 네트워크 LLM의 해석 능력을 평가하기 위해서는 단순한 지식 기반 질의응답을 넘어, 실제 설정 파일에서 사실을 추출하고 경로를 추론하며 장애 영향을 분석하는 다단계 인지 능력을 측정할 수 있는 벤치마크가 필요하다.
% 이를 위하여 우리는 실제 Cisco IOS 설정 파일(\texttt{.cfg}) 입력을 기반으로 5단계 인지 난이도의 QA 쌍을 자동 생성하는 벤치마크 \textbf{NetConfigQA~2.1}을 구축한다.
% \textbf{NetConfigQA~2.1}은 토폴로지 설계, 이중 경로 생성 파이프라인, 인지 난이도 체계, 그리고 네트워크 데이터에 특화된 평가 지표 TA-Acc의 네가지의 요소로 구성된다.

\subsection{Five-Level Cognitive Difficulty Taxonomy}
% ============================================================
\input{tables/difficulty_taxonomy}

The ability of LLMs to interpret configuration files varies significantly depending on question complexity.
Reading a configuration value from a single device and inferring a packet path by synthesizing configurations across multiple devices require qualitatively different cognitive capabilities.
To systematically measure these differences, we design a five-level difficulty taxonomy based on the cognitive load of network operators, as shown in Table~\ref{tab:difficulty_taxonomy}.

Levels L1--L3 belong to the \textbf{Static Analysis} domain, where answers can be derived directly from configuration file text.
L1 covers fact extraction: reading a specific value from a single device; L2 involves statistical aggregation by traversing all devices; and L3 requires cross-comparison of configurations across multiple devices to identify logical inconsistencies.
Levels L4--L5, by contrast, fall under the \textbf{Dynamic Reasoning} domain: although all necessary information is present in the configuration, deriving the answer requires executing graph algorithms (e.g., OSPF SPF).
L4 involves path inference by simulating packet traversal hop-by-hop, while L5 performs what-if analysis to assess the impact of link or device failures on the network.

% 단순히 설정 값을 읽는 것과 여러 장비의 설정을 종합하여 패킷 경로를 추론하는 것은 요구되는 인지 능력이 질적으로 다르기 때문이다.
% 이를 체계적으로 측정하기 위하여, 본 논문에서는 네트워크 운영자의 인지 부하(Cognitive Load)를 기준으로 Table~\ref{tab:difficulty_taxonomy}과 같이 5단계 난이도 체계를 설계한다. 5단계 난이도의 각 설명은 다음과 같다.
% L1-L3는 설정 파일의 텍스트에서 직접 답을 도출할 수 있는 Static Analysis의 영역이다.
% L1은 단일 장비에서 특정 값을 읽는 사실 추출, L2는 전체 장비를 순회하여 통계를 집계하는 작업, L3는 복수 장비의 설정을 교차 비교하여 논리적 모순을 찾는 작업에 해당한다.
% L1-L3와 다르게 L4-L5는 설정에 필요한 정보가 모두 포함되어 있으나 그래프 알고리즘(OSPF SPF 등)의 실행이 요구되는 Dynamic Reasoning의 영역이다. L4는 실제 패킷 경로를 hop-by-hop으로 시뮬레이션하는 경로 추론이며, L5는 특정 링크나 장비의 장애 발생 시 네트워크에 미치는 영향을 분석하는 what-if 추론이다.

\subsection{Topology Design}
% ============================================================

\input{tables/topology}
To observe how the interpretive capability of LLMs changes with topology scale, we design four topologies at 10-node intervals (Table~\ref{tab:topology-summary}).

The base topology, Lab-A, is a 10-node Service Provider MPLS VPN network built on Cisco IOS routers. It connects four P (Provider) routers, two PE (Provider Edge) routers, and four Leaf switches using OSPF, MP-BGP, LDP, and VRF. This protocol combination reflects real-world operational environments.

Lab-B through Lab-D incrementally extend the topology and protocol set of Lab-A.
Lab-B (20 nodes) adds management protocols such as NTP, SNMP, and AAA to increase operational complexity.
Lab-C (30 nodes) introduces L2VPN, ACL, eBGP, and HSRP to reflect security and redundancy scenarios.
Lab-D (40 nodes) incorporates a multi-AS configuration spanning three autonomous systems, along with QoS and NetFlow, to emulate a large-scale ISP environment.

Configuration files for Lab-B through Lab-D are automatically generated from Lab-A using a YAML-based topology definition and a Jinja2 template-based configuration generator. Protocol convergence (OSPF/BGP/LDP) is verified after deployment in the PNETLab emulation environment.
By replacing only the topology definition while keeping the same pipeline and policy file, we demonstrate automatic dataset scaling proportional to configuration complexity.

The per-level QA distribution is summarized in Table~\ref{tab:topology-summary}.
L1 question counts remain constant across labs because the number of device-level metrics (e.g., hostname, interface IP) is fixed regardless of topology size; adding new protocols after Lab-B does not increase the number of L1 questions.
L2 consists of global-scope metrics (e.g., ``proportion of devices with SSH enabled'') and is independent of node count. The number of L2 questions decreases slightly as protocol diversity changes.
L4, which queries the packet path between two arbitrary devices, grows in proportion to the number of source–destination pairs, $N \times (N-1)$, resulting in an $O(N^2)$ increase. Accordingly, the number of L4 instances rises from 146 in Lab A (10 nodes) to 1,657 in Lab D (40 nodes).
These results show that the proposed pipeline automatically generates more QA pairs as topology scale increases.
The QA-per-node (QA/N) ratio remains stable in the range of 84--126, confirming the linear scalability of the pipeline.

\subsection{Dual-Path QA Generation Pipeline}
% ============================================================

While answers to L1--L3 questions can be derived directly from configuration file text, L4--L5 questions require the execution of graph algorithms such as OSPF SPF computation or fault propagation analysis.
To address this, NetConfigQA~2.1 adopts a Dual-Path pipeline that handles two fundamentally different reasoning paradigms—static analysis (L1--L3) and dynamic simulation (L4--L5)—using the most suitable engine for each.
L1--L3 are processed via a rule-based path (Path~A), whereas L4--L5 are handled via a procedural path (Path~B).
Manually constructing QA pairs would incur labor costs that grow with topology scale and make consistency difficult to maintain. Therefore, both paths are designed to automatically generate QA pairs from configuration files.

% % 스킬 분석: Dual-Path에 동기(motivation) 문장 추가 — "왜 두 경로인가"
% L1-L3는 설정 파일의 텍스트에서 직접 정답을 도출할 수 있지만, L4-L5는 OSPF SPF 계산이나 장애 전파와 같은 그래프 알고리즘의 실행 없이는 정답을 구할 수 없다.
% 이를 해결하기 위해, NetConfigQA~2.1은 Dual-Path 파이프라인을 구성하여 정적 분석(L1-L3)과 동적 시뮬레이션(L4-L5)이라는 근본적으로 다른 두 가지 추론 방식을 각각 최적의 엔진으로 처리한다.
% 설정 파일의 정적 분석이 가능한 L1-L3는 규칙 기반 경로(경로~A)로, 시뮬레이션이 필요한 L4-L5는 절차적 경로(경로~B)로 처리한다.
% 또한 QA 쌍을 수작업으로 구성하면 토폴로지 규모에 비례하여 인력 비용이 급증하고 일관성을 유지하기 어렵기 때문에, 두 경로 모두 설정 파일로부터 자동으로 QA를 생성하도록 설계한다.


\textbf{Path A (L1--L3, Rule-Based):}
The formal network analysis tool Batfish~\cite{ref17} parses configuration files and produces a JSON representation of static facts.
The 127 metrics defined in \texttt{policies.json} define the set of items that network operators routinely verify for a given topology (e.g., interface states, routing neighbors, ACL rules). These metrics are organized based on the Cisco IOS operations manual and the analysis scope supported by Batfish.
Each metric specifies a question template, a scope expansion rule, and an answer type.

The Scope Expansion mechanism dynamically generates question instances across 12 scope types (GLOBAL, DEVICE, DEVICE\_PAIR, AS, OSPF\_AREA, VRF, FLOW, etc.). Since each metric is instantiated for every applicable entity in the topology, the number of QA pairs naturally scales with the number of nodes.
The monotony of template-based questions is mitigated through scope expansion (dynamic substitution of device names, VRF names, and interface names) and combinatorial node-pair sampling for L4/L5.
This design ensures that deriving correct answers requires understanding the topology structure rather than relying on keyword matching.

% \textbf{경로 A (L1-L3, 규칙 기반):}
% 네트워크 정형 검증 도구인 Batfish~\cite{ref17}가 설정 파일을 파싱하여 정적 사실(Static Facts) JSON을 생성한다. \texttt{policies.json}에 정의된 127개 메트릭은 네트워크 운영자가 토폴로지에 대해 일상적으로 확인하는 항목 (인터페이스 상태, 라우팅 이웃, ACL 규칙 등)을 Cisco IOS 운영 매뉴얼과 Batfish가 지원하는 분석 범위를 기준으로 체계화한 것이다.

% 스코프 확장(Scope Expansion) 메커니즘은 12가지 스코프 타입(GLOBAL, DEVICE, DEVICE\_PAIR, AS, OSPF\_AREA, VRF, FLOW 등)에 걸쳐 질문 인스턴스를 동적으로 생성하며, 하나의 메트릭이 토폴로지 내 모든 해당 엔티티에 대해 자동으로 인스턴스화되므로 노드 수 증가에 비례하여 QA가 자연스럽게 확장된다.
% 템플릿 기반 생성에서 발생할 수 있는 질문 형태의 단조로움은, 스코프 확장 메커니즘(장비명, VRF명, 인터페이스명의 동적 치환)과 L4/L5의 조합적 노드 쌍 샘플링을 통해 완화한다.
% 후자는 키워드 오버피팅이 아닌 토폴로지 구조 이해를 정답 도출의 전제 조건으로 만든다.


\textbf{Path B (L4--L5, Procedural):}
Although configuration files contain all necessary information for path computation, verifying actual packet paths or fault impact requires executing graph algorithms. To this end, we use the Batfish simulation engine.

For L4, node pairs are sampled, and \texttt{traceroute} and \texttt{reachability} queries are executed.
For L5, \texttt{fork\_snapshot} creates a virtual copy of the network with designated links or nodes deactivated, and \texttt{differentialReachability} queries are used to analyze fault impact. The results from Path~B via Batfish are automatically converted into natural language QA pairs.

The complete pipeline is illustrated in Fig.~\ref{fig:pipeline}.

\subsection{Type-Aware Accuracy (TA-Acc)}
% ============================================================

In designing the evaluation metric for this benchmark, we observe that conventional NLP metrics are structurally ill-suited for network configuration data.
BERTScore assigns a similarity of 0.9 or higher to semantically distinct IP addresses (\texttt{10.0.1.1} and \texttt{10.0.1.10}), thus failing to discriminate between models.
Exact Match treats sets that differ only in ordering (\texttt{\{r1,~r2\}} vs.\ \texttt{\{r2,~r1\}}) as incorrect.
Token F1 ignores path ordering, treating reverse paths (\texttt{PE1$\rightarrow$P1$\rightarrow$R1} vs.\ \texttt{R1$\rightarrow$P1$\rightarrow$PE1}) as equivalent.
To overcome these shortcomings, we propose \textbf{Type-Aware Accuracy (TA-Acc)}, which applies a comparison function appropriate to each answer type.

% 벤치마크의 평가 지표를 설계하는 과정에서, 기존 NLP 평가 지표가 네트워크 구성 데이터에 구조적인 어려움이 따른다.
% BERTScore는 의미적으로 다른 IP 주소(\texttt{10.0.1.1}과 \texttt{10.0.1.10})에 0.9 이상의 유사도를 부여하여 모델 간 차이를 변별하지 못한다.
% Exact Match는 집합의 순서 차이(\texttt{\{r1,~r2\}} vs \texttt{\{r2,~r1\}})를 오답으로 처리한다.
% Token F1은 경로의 순서를 무시하여 역방향 경로(\texttt{PE1$\rightarrow$P1$\rightarrow$R1}과 \texttt{R1$\rightarrow$P1$\rightarrow$PE1})를 동등하게 평가한다.
% 기존 평가 지표의 부적합을 해소하기 위해 우리는 답변 타입별로 적합한 비교 함수를 적용하는 \textbf{Type-Aware Accuracy (TA-Acc)}를 제안한다.


\textbf{Definition.}
Given a dataset $D = \{(q_i, g_i, t_i)\}_{i=1}^{N}$, where $q_i$ denotes the question, $g_i$ the ground truth, and $t_i$ the answer type, and corresponding model predictions $p_i$, TA-Acc is defined as
\begin{equation}
  \text{TA-Acc}(D) = \frac{1}{N} \sum_{i=1}^{N} f_{t_i}(\hat{p}_i, \hat{g}_i)
  \label{eq:taacc}
\end{equation}
where $\hat{p}_i$ and $\hat{g}_i$ are the normalized forms of the prediction and the ground truth, respectively (e.g., lowercasing, CIDR notation removal, null value consolidation).
The comparison function $f_t$ is defined separately for the seven answer types listed in Table~\ref{tab:taacc-types}. The type definitions are grounded in the YANG data model (RFC~6020) and SNMP tabular MIB (RFC~2578) standards.

% 비교 함수 $f_t$는 Table~\ref{tab:taacc-types}에 정의된 7가지 타입별로 다르게 적용된다.
% 각 타입 명칭은 네트워크 관리 표준인 YANG 데이터 모델(RFC~6020)과 SNMP 테이블형 MIB(RFC~2578)에 근거하여 정의하였다.

The Resource Inventory and Property/Metric Table types return continuous scores between 0 and 1 using the F1 score.
Specifically, for a predicted set $P$ and ground-truth set $G$:
\begin{equation}
  f_{\texttt{set}}(P, G) = \frac{2 \cdot |P \cap G|}{|P| + |G|}
  \label{eq:set-f1}
\end{equation}
The Property / Metric Table type treats (key, normalized value) pairs as set elements and applies the same F1 formulation.
The remaining four types (Scalar Attribute, Forwarding Sequence, Scalar Counter, Configuration State) return binary scores (0 or 1), with type-specific normalization applied. In particular, the Forwarding Sequence type uses Ordered Exact Match to preserve node ordering, thereby distinguishing \texttt{R1$\rightarrow$P1$\rightarrow$PE1} from \texttt{PE1$\rightarrow$P1$\rightarrow$R1}.
Token F1 fallback is intentionally omitted, as it assigns disproportionately high scores to partial matches in network data, degrading discriminability between models.

\textbf{Aggregation.}
Micro-average over all QA pairs is used as the primary metric; level-macro average is additionally computed to control for the effect of unequal level distributions.
The level-macro average first computes TA-Acc for each level and then takes the arithmetic mean across the five levels, making it useful for identifying discrepancies with the micro-average in large-scale topologies where L4 questions dominate.

\subsection{Ground Truth Validation}

The reliability of the benchmark depends on the accuracy of its ground truth (GT).
In this paper, GT is defined using formal network analysis with Batfish~\cite{ref17}, a network simulator that performs deterministic analysis based on configuration files.
Batfish is an established tool in the network formal verification community, alongside Header Space Analysis~\cite{ref22}, VeriFlow~\cite{ref23}, and Minesweeper~\cite{ref24}.

It has been used as an oracle in NetConfEval~\cite{wang2024netconfeval}. In addition, Config2Spec~\cite{ref20} and DNA~\cite{ref25} perform configuration specification extraction and differential analysis on top of Batfish, while Campion~\cite{ref29} automatically debugs behavioral differences between router configuration pairs.
Brown et al.~\cite{ref32} document Batfish's evolution from a research prototype to an industrial tool, further supporting its reliability.

To independently validate GT accuracy, three methods are applied.

The seemingly low overall agreement rate of approximately 92\% for Lab-B through Lab-D does not indicate GT errors but rather reflects the coverage limitations of the independent parser.
Simulation-dependent metrics (e.g., L4/L5 traceroute results) cannot in principle be re-derived by a Python+Regex parser and are therefore counted as mismatches; these cases are validated separately using Method~3 (PNETLab CLI).
Classifying the sources of mismatch shows simulation dependency (57\%), Batfish parsing limitations (37\%), and independent parser limitations (6\%); actual factual mismatches in static facts total just one instance across all four labs ($<$0.02\%).
In summary, the ``static verification range'' (98--99.9\%) represents the true accuracy of the L1--L3 GT, while the lower overall agreement rate reflects limitations of the validation method rather than any decline in GT quality.

\textbf{Method~2 (Stratified Manual Validation):}
For each lab, 67--73 stratified random samples per level were drawn, and the accuracy of the question-answer pairs was cross-validated by directly inspecting the original \texttt{.cfg} files.
Validation was restricted to L1--L3 static facts; validators directly examined the relevant configuration syntax to judge agreement with Batfish parsing results.
No discrepancies were found across any of the four labs.

\textbf{Method~3 (PNETLab Physical Device CLI):}
To validate the reliability of L4--L5 simulation-based answers, 44--47 samples per lab were evaluated by executing commands such as \texttt{show ip route}, \texttt{traceroute}, and \texttt{show ip ospf neighbor} on the Cisco IOS CLI within the PNETLab emulation environment, and comparing the outputs against Batfish simulation results.
No discrepancies between the physical device CLI outputs and the Batfish ground truth were observed, confirming that Batfish accurately reproduces actual network behavior for the topologies considered in this study.

\textbf{GT Independence.}
A circular dependency exists because both the L4--L5 Ground Truth and NetAlly rely on Batfish; mitigation strategies for this issue are discussed in Section~5.
