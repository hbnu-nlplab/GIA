# 슬라이드 2 (Method 1/2): 구조적 답변 평가 (Set & Map)

## "순서와 형식이 달라도, 의미가 같으면 정답입니다"

### 1. Set Type (순서 무관 & F1 Score)
리스트를 **집합(Set)**으로 변환하여 **순서를 무시**하고 구성 요소만 비교합니다.
일부만 맞을 경우 **Precision/Recall 기반 F1 Score**로 부분 점수를 부여합니다.


- **정답**: `["GigabitEthernet0/0", "GigabitEthernet0/1", "Loopback0"]` (3개)

| 모델 예측 (Prediction) | **채점 방식** | 점수 | 판정 이유 |
|:---|:---|:---:|:---|
| `["Loopback0", "Gi0/0", "Gi0/1"]` | **Set F1** | **1.0** | 순서가 바뀌었지만 구성 요소 일치 |
| `["Gi0/0", "Gi0/1"]` | **Set F1** | **0.8** | 3개 중 2개 맞춤 (Recall 0.67 반영) |
| `["Loopback0", "Gi0/0", "Gi0/1"]` | Exact Match | 0.0 | 문자열 순서 다름 |

### 2. Map Type (Key/Value 분리 & 정규화)
JSON을 파싱하여 **전체 Key 대비 탐색률(50%)**과 **찾은 Key 중 Value 정확도(50%)**를 합산하여 채점합니다.
모델이 정보를 얼마나 유실 없이 찾아냈는지(Coverage)와 찾아낸 정보가 얼마나 정확한지(Accuracy)를 동시에 반영합니다.
Value 정규화 시 **IP 주소의 CIDR 제거** 및 **네트워크 상태값(shutdown→down)** 통일 과정을 거쳐 의미적 일치를 판단합니다.

**실제 데이터 (ID: `INTERFACE_IP_MAP` - leaf2 장비)**
- **정답**: `{"Gi0/0": "172.16.2.2/24", "Gi0/1": "", "Gi0/2": "10.10.2.1/24", "Gi0/3": "10.10.10.32/24"}` (4개)

| 모델 예측 (Prediction) | **채점 방식** | 점수 | 판정 이유 |
|:---|:---|:---:|:---|
| `{"Gi0/0": "172.16.2.2", ...}` | **Map Score** | **1.0** | `172.16.2.2/24` == `172.16.2.2` (CIDR 무시) |
| `{"Gi0/0": "172.16.2.2", "Gi0/2": "10.10.2.1"}` | **Map Score** | **0.75** | Key 2/4(50%×0.5=0.25) + Value 2/2(100%×0.5=0.5) |
| `{"Gi0/0": "172.16.2.3/24"}` | **Map Score** | **0.0** | IP 주소 값 불일치 (`.2` vs `.3`) |

**실제 데이터 (ID: `INTERFACE_STATUS_MAP` - leaf4 장비)**
- **정답**: `{"Gi0/1": "down", ...}`

| 모델 예측 (Prediction) | **채점 방식** | 점수 | 판정 이유 |
|:---|:---|:---:|:---|
| `{"Gi0/1": "shutdown"}` | **Map Score** | **1.0** | `shutdown` → `down` 자동 정규화 |
| `{"Gi0/1": "shutdown"}` | Exact Match | 0.0 | 문자열 `"down"` vs `"shutdown"` 다름 |

# 슬라이드 3 (Method 2/2): 의미적 답변 평가 (Numeric & Text)

## "표현 방식이 다양해도, 값이 같으면 정답입니다"

### 3. Numeric Type (값 추출 & 비교)
정규식과 영어 단어 사전을 사용하여 텍스트에서 **숫자 값만 추출**합니다.
추출된 두 값을 **수치적으로 비교**하여 일치 여부를 판단합니다.

**실제 데이터 (ID: `INTERFACE_COUNT` - leaf1 장비)**
- **질문**: "Leaf1의 인터페이스 개수는?" (정답: `4`)

| 모델 예측 (Prediction) | **채점 방식** | 추출 값 | 점수 | 설명 |
|:---|:---|:---:|:---:|:---|
| `"4"` | **Value Compare** | 4.0 | **1.0** | 단순 숫자 일치 |
| `"총 4개입니다."` | **Value Compare** | 4.0 | **1.0** | 문장에서 정규식으로 숫자 추출 |
| `"총 4개입니다."` | Exact Match | - | 0.0 | 뒤에 붙은 "개입니다" 때문에 오답 |

### 4. Text Type (2단계 평가: 전처리 + Hybrid Scoring)
먼저 LLM의 지저분한 출력에서 **핵심 답변을 추출(Parsing)**하고,
추출된 답변을 **정규화된 Exact Match**로 1차 평가한 후, 실패 시 **Token F1**로 부분 점수를 부여합니다.

**실제 데이터 예시 (Traceroute 경로)**
- **질문**: "pe1에서 10.0.0.1까지의 경로를 나열해주세요."
- **정답 (Gold)**: `"pe1 → p2"`
- **원본 LLM 출력 (raw_pred)**: `"<think>분석...</think>PE1→P2"`

**[Step 1: Parsing]** `<think>` 태그, 서술어 제거 → **`"PE1→P2"`**

**[Step 2: Normalized EM 또는 Token F1]**

| 파싱 후 모델 답변 | **채점 방식** | 점수 | 판정 이유 |
|:---|:---|:---:|:---|
| `"PE1→P2"` | **Normalized EM** | **1.0** | 대소문자 정규화 (`PE1` == `pe1`) |
| `"pe1 -> p2"` | **Normalized EM** | **1.0** | 화살표 정규화 (`->` == `→`) |
| `"경로는 pe1 → p2 입니다"` | **Token F1** | **~0.6** | EM 실패 → 핵심 토큰 교집합 기반 부분 점수 |

# 슬라이드 4 (Why?): 왜 TA-Acc가 필요한가? (Necessity)

## "기존 메트릭은 네트워크 설정 검증에 위험합니다"

단일 메트릭(Token F1 등)을 일괄 적용할 때 발생하는 **두 가지 치명적인 문제**를 해결합니다.

### 🔴 문제 1: 치명적 오류를 높은 점수로 평가 (False Positive)
IP 주소 오류는 네트워크에서 치명적이지만, 텍스트 유사도 기반 메트릭은 이를 잡아내지 못합니다.

- **사례**: 정답 `10.0.0.1` vs 예측 `10.0.0.2` (완전히 다른 장비)
- **Token F1**: **85.7%** (높은 점수) ⚠️
- **TA-Acc**: **0%** (정확한 오답 처리 - Numeric/Map) ✅

### 🔵 문제 2: 정답을 오답으로 평가 (False Negative)
순서/형식의 사소한 차이로 인해 올바른 추론 능력이 저평가됩니다.

- **사례**: 정답 `["A", "B"]` vs 예측 `["B", "A"]`
- **Exact Match**: **0%** (완전 오답 처리) ⚠️
- **TA-Acc**: **100%** (정당한 정답 처리 - Set) ✅

### 💡 결론 (Conclusion)
> **"TA-Acc는 '관대해야 할 때(순서/형식)'는 유연하고,**
> **'엄격해야 할 때(IP/수치)'는 정확하게 평가하는**
> **네트워크 도메인 특화(Domain-Specific) 평가 방식입니다."**
